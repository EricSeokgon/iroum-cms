# iroum-cms 제품 문서

> 상세 요구사항은 SPEC-CMS-001 참조 (작성 예정)

---

## 1. 제품 정체성

| 항목 | 내용 |
|------|------|
| 프로젝트명 | iroum-cms |
| 유형 | 공공기관 일반 CMS (Content Management System) |
| 표준 | 전자정부 표준프레임워크 v5.0.0 + 공통컴포넌트 v5.0 |
| 한 줄 정의 | 전자정부 표준을 준수하는 운영자 친화적 공공기관 차세대 CMS |

---

## 2. 비전 — 초안, 검토 필요

> 아래 비전 선언문은 초안입니다. 실제 서비스 목표와 기관 특성에 맞춰 1~2문장으로 다듬어 주세요.

**초안 비전:**
공공기관 표준(전자정부 프레임워크 v5)을 충실히 따르면서, 운영자가 직관적으로 콘텐츠를 관리하고 시민이 어느 기기에서나 접근 가능한 웹 접근성·다국어 기반의 차세대 CMS를 제공한다.

**보완이 필요한 요소 (검토 요청):**
- 서비스 대상 기관명 또는 기관 유형 명시 여부
- "차세대"의 구체적 의미 (기존 시스템 대비 개선점 강조 여부)
- 다국어 지원 범위 (한국어 + 영어 기본, 추가 언어 여부)

## 3. 타겟 사용자

### Primary 페르소나: 공공기관 콘텐츠 관리자

- 역할: 기관 웹사이트의 공지사항, 게시글, 페이지 콘텐츠 등을 작성·발행하는 담당자
- 특성: 비개발 직군, 워드프로세서 수준의 IT 소양, 정기적 콘텐츠 업데이트 업무
- 주요 요구: 직관적인 에디터, 반복 작업 자동화, 오탈자 없는 발행 워크플로우
- 핵심 불편: 복잡한 기존 시스템, 느린 로딩, 접근성 검수 수작업

### Primary 페르소나: 시스템 운영자 (관리자)

- 역할: 사용자 계정, 권한, 메뉴 구조, 코드 관리, 감사로그 점검
- 특성: IT 담당자 또는 외주 유지보수 업체, 전자정부 표준프레임워크 운영 경험
- 주요 요구: 안정적인 권한 관리, 명확한 감사 추적, 시스템 모니터링 대시보드
- 핵심 불편: 분산된 관리 메뉴, 로그 조회 어려움, 표준 프레임워크 버전 호환성 문제

### Secondary 페르소나: 일반 시민 방문자

- 역할: 공공기관 웹사이트를 통해 공지사항·정보를 조회하는 일반 시민
- 특성: 다양한 연령대, 장애인 포함, 모바일·PC 혼용
- 주요 요구: 빠른 페이지 로딩, 스크린리더 호환, 명확한 정보 탐색
- 핵심 불편: 접근성 미준수 인터페이스, 느린 응답 속도

## 4. 비즈니스 목표

| 번호 | 목표 | 연결 KPI |
|------|------|----------|
| 1 | 운영 효율 향상 | 콘텐츠 작성→발행 소요 시간 50% 단축 |

| 4 | 확장 가능 구조 확보 | Docker 기반 배포, K8s 전환 가능, 멀티사이트 구조 지원 |

## 5. 성공 기준

### 정량 기준 — 초안, 검토 필요

| 지표 | 목표값 | 측정 방법 |
|------|--------|----------|
| LCP (Largest Contentful Paint) | < 2.5초 | Lighthouse / Web Vitals |
| KWCAG 2.2 AA 자동 검사 실패 | 0건 | axe-core 자동화 검사 |
| 감사로그(audit log) 누락률 | 0% | 로그 무결성 검증 |
| 신규 운영자 적응 기간 | 1주 내 핵심 기능 습득 (95% 이상) | 사용자 테스트 |
| 테스트 커버리지 | 85% 이상 | JaCoCo (BE) + Vitest Coverage (FE) |

### 정성 기준

- 공공기관 납품 후 추가 커스터마이징 없이 운영 가능한 완성도
- 전자정부 공통컴포넌트 표준 화면 대비 운영자 만족도 향상
- 장애인 사용자 포함 모든 시민이 동등하게 정보에 접근 가능

## 6. 1차 출시 범위

1차 SPEC(SPEC-CMS-001)에서 구현할 전자정부 공통컴포넌트 4개 묶음. 각 묶음의 상세 요구사항은 SPEC 문서에서 다룸.

### A. 회원·권한·로그인

- 사용자 관리 (uss/umt): 회원 가입, 계정 관리, 정보 수정
- 권한 관리 (sec/rmt): 메뉴·기능 단위 권한 매트릭스
- 역할 관리 (sec/aut): 역할 정의 및 사용자-역할 매핑
- 로그인 (uat/uia): JWT 기반 인증, 세션 관리, 보안 정책

### B. 게시판·공지·Q&A·FAQ

- 게시판 (cop/bbs): 일반/갤러리형, 페이징, 댓글 선택 적용
- 공지사항 (cop/ntc): 중요 공지 고정, 팝업 공지 연동
- FAQ·Q&A (cop/com/faq, qna): 카테고리별 질의응답, 관리자 답변
- 첨부파일 관리 (cop/cmm/fms): 파일 업로드, 확장자 검증, 보안 다운로드
- 게시물 별점 리뷰 (SPEC-CMS-REVIEW-001): 인증 사용자가 게시물에 별점(1-5) + 리뷰 텍스트 작성, 다중 리뷰 허용, 게시물 단위 평균 별점 집계 노출, 관리자 중앙 모더레이션(목록/숨김/삭제)

### C. 콘텐츠·메뉴·사이트관리

- 메뉴 관리 (sym/mnu): 트리 구조, 권한별 메뉴 노출 제어
- 템플릿 관리 (uss/ion/tmm): 페이지 레이아웃 템플릿
- 사이트·페이지·콘텐츠 관리: 위지윅 에디터, 버전 이력
- 팝업·배너 관리: 기간 설정, 위치별 노출

### D. 통계·로그·시스템관리

- 접속로그·통계 (sym/log): 방문자 통계, 검색어 통계
- 코드 관리 (sym/ccm): 공통 코드 그룹 및 상세 코드 CRUD
- 시스템 운영 대시보드: 서버 상태, 최근 감사로그, 알림

**예상 규모:** SPA 페이지 60~80개 (관리자 백오피스 40~50 + 공공 웹사이트 20~30)

## 7. 비범위 (Out of Scope) — 1차 제외

다음 기능은 1차 출시 범위에서 제외됩니다. 추후 SPEC에서 별도 기획 필요.

| 항목 | 제외 사유 |
|------|----------|
| 소셜 로그인 (카카오, 네이버 등) | 공공기관 보안 정책상 기관 자체 계정 우선, 별도 검토 필요 |
| GPKI / 공동인증서 (공인인증서) 연동 | 전문 외부 라이브러리 및 법적 검토 필요, 별도 SPEC |
| 모바일 네이티브 앱 (iOS/Android) | 웹 기반 반응형으로 우선 대응 |
| AI 기반 콘텐츠 추천·자동 생성 | 공공기관 AI 도입 절차 별도 필요 |
| 전자결재·그룹웨어 연동 | 기관별 시스템 상이, 커스터마이징 대상 |
| 다중 데이터베이스 지원 (Oracle, MySQL 등) | 1차는 PostgreSQL 단일 지원 |
| 멀티테넌시 (SaaS형 다기관 운영) | 아키텍처 복잡도 고려, 추후 확장 대상 |

## 8. 제약 및 가정

### 법적·표준 준수 — 고정

- KWCAG (한국형 웹 콘텐츠 접근성 지침) 2.2 레벨 AA 준수 의무
- 개인정보보호법 준수: 개인정보 최소 수집, 암호화 저장, 처리방침 게시
- 감사로그 보존: 시스템 접근·조작 이력 의무 기록 (기간은 기관 정책에 따름)
- 전자정부 표준프레임워크 v5 호환 유지

### 인프라 가정 — 초안, 검토 필요

- 초기 배포 환경: Docker + docker-compose 기반 단일 서버 또는 소규모 클러스터
- 운영 이관 시 K8s 전환 가능한 컨테이너 구조 유지
- CI/CD: GitHub Actions (상세 파이프라인은 SPEC-CMS-001 이후 확정)
- 외부 이메일 서버 연동 여부: 미확정 (알림 기능 구현 시 확인 필요)

### 기술 가정

- 신규 프로젝트(그린필드)로 레거시 마이그레이션 불필요
- 개발 방법론: TDD (quality.yaml 설정값 기준)
- 테스트 커버리지 목표: 85% (커밋당 최소 80%)
- 코드 주석 언어: 한국어 (language.yaml code_comments: ko)
