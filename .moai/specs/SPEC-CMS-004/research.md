# SPEC-CMS-004 Research — Bundle C 설계 의사결정 기록

## 1. 메뉴 트리 모델: Adjacency List + Materialized Path 하이브리드

### 검토 옵션

| 옵션 | 장점 | 단점 | 채택 |
|------|------|------|:--:|
| Adjacency List (parent_id만) | 가장 단순, 삽입/이동 저렴 | 전체 트리 조회 시 N+1 또는 재귀 CTE 필요 | △ |
| Materialized Path (path 컬럼) | 트리 prefix 쿼리 1회로 빠름, 정렬 자연 | parent 변경 시 자손 path 일괄 갱신 비용 | △ |
| Nested Set (lft/rgt) | 서브트리 조회 1쿼리 | 삽입/이동 시 다수 row 갱신, 동시성 복잡 | × |
| Closure Table | 임의 깊이 조회 우수 | 추가 테이블 + 모든 조상 행 유지 비용 | × |
| **하이브리드 (parent_id + path)** | **삽입/이동 단순, 조회 빠름, 정렬 자연** | 이동 시 자손 path 갱신 필요 (한 번에 처리) | **✓** |

### 결정

**Adjacency List(`parent_id`) + Materialized Path(`path`) 하이브리드 채택.**
- 삽입·CRUD는 parent_id로 단순 처리
- 트리 조회는 path text_pattern_ops 인덱스로 prefix 쿼리 또는 path 정렬로 1쿼리 처리
- 이동 시 자손 path 갱신은 트리거가 아닌 서비스 레이어 트랜잭션에서 처리(트리거는 deadlock 위험)
- depth 컬럼 추가로 5단계 제약 즉시 검증

근거: 공공기관 메뉴는 깊이 5 이내, 빈도 변경 적음, 노출은 매 요청. 조회 성능 우선.

## 2. 콘텐츠 본문: 블록 기반 vs 단일 HTML 본문

### 검토 옵션

| 옵션 | 장점 | 단점 |
|------|------|------|
| 단일 HTML 본문 (TEXT 컬럼) | 위지윅 그대로 저장, 단순 | 다국어 시 본문 통째 복제, 재사용성·A/B 불가, 부분 수정 어려움 |
| **블록 기반 (content_block 테이블)** | 다국어는 블록별 i18n 가능, 재사용성, 정렬·교체 용이, 향후 A/B 테스트 여지 | 스키마 복잡도 증가, 렌더링 시 N 블록 조회 |
| 외부 CMS 헤드리스 | 전문성 | 종속성·운영 부담 |

### 결정

**블록 기반 채택.**
- block_type 5종(RICH_TEXT/IMAGE/HTML/MARKDOWN/EMBED)으로 시작
- payload jsonb로 타입별 스키마 유연
- 다국어 i18n_resource 테이블에서 block payload 필드 단위 번역
- 페이지당 평균 10~30 블록, 인덱스 `(page_id, sort_order)` 만으로 충분

## 3. 페이지 이력 저장: 풀 스냅샷 vs 델타

### 검토 옵션

| 옵션 | 장점 | 단점 |
|------|------|------|
| **풀 스냅샷 (jsonb)** | 조회·롤백 단순(스냅샷 그대로 적용), 복잡한 diff 알고리즘 불필요 | 저장 용량 증가 |
| 델타(JSON Patch) | 저장 효율 | 롤백 시 누적 적용, 중간 손상 시 모든 후속 무효 |
| 외부 객체 스토리지 | 핫스토리지 절감 | 인프라 의존성, 1차 부담 |

### 결정

**풀 스냅샷 jsonb 채택.**
- 페이지 평균 본문 50KB 가정, 100회 수정 시 5MB → 10년 보존도 50GB 미만 수용 가능
- 90일 이후 외부 스토리지 이관(후속 SPEC)
- 페이지 row + 모든 블록 + 모든 i18n_resource를 한 번에 jsonb로 직렬화

## 4. 다국어 모델

### 검토 옵션

| 옵션 | 장점 | 단점 |
|------|------|------|
| 컬럼 분리 (title_ko, title_en) | 단순 | 언어 추가 시 스키마 변경, NULL 다수 |
| jsonb 컬럼 (`{"ko":"...","en":"..."}`) | 스키마 안정, 추가 자유 | 부분 인덱스/검색 불편, FTS 호환 약함 |
| **별도 정규화 테이블 (i18n_resource)** | 언어 추가 시 스키마 무변경, 누락 감지 쉬움, FTS 호환, 폴백 로직 단일 | 조회 시 join 1회 추가 |

### 결정

**별도 정규화 테이블 `i18n_resource(namespace, resource_id, language, field_name, value)` 채택.**
- 1차는 ko/en 2개. 3개 이상 도입 시 스키마 변경 없이 행 추가만으로 확장
- 캐시 키 `i18n:{ns}:{id}:{lang}` 로 join 비용 흡수
- SPEC-CMS-001 §6.5 REQ-CROSS-007 (`content_i18n` 복합키)와 정합 — 본 SPEC이 더 일반화된 형태로 흡수.

## 5. SEO sitemap.xml 생성 전략

### 검토 옵션

| 옵션 | 장점 | 단점 |
|------|------|------|
| 동적 매 요청 생성 | 항상 최신 | 10k+ 페이지 시 응답 지연 |
| 정적 파일 일괄 생성 (배치) | 응답 즉시 | 발행 후 반영 지연(배치 주기) |
| **캐시 + 무효화 (TTL 1h + 이벤트 기반)** | 최신성·성능 양립 | 캐시 인프라 필요(1차 Caffeine OK) |

### 결정

**캐시 + 이벤트 무효화 채택.**
- TTL 1시간 자체 폴백 (캐시 누락 시 자동 재생성)
- 페이지 publish/retract/slug 변경 이벤트에 즉시 무효화
- 10k 페이지 기준 생성 비용 < 1s 측정 목표

## 6. 팝업 노출 빈도 제어

### 검토 옵션

| 옵션 | 장점 | 단점 |
|------|------|------|
| **쿠키 (popup_close_{id}=YYYYMMDD)** | 표준, 비로그인 지원, 브라우저 단위 | 개발자도구로 쉽게 우회 |

**쿠키 우선, 베스트 에포트 정책 채택.**
- 일반 안내 팝업은 쿠키로 충분
- 강제 차단이 필요한 캠페인(법적 고지 등)은 후속 SPEC에서 서버 카운트 도입

## 7. 캐시 인프라

### 검토 옵션

| 옵션 | 장점 | 단점 |
|------|------|------|
| **Caffeine (인메모리, JVM 내)** | 무인프라, 응답 µs 단위, Spring `@Cacheable` 호환 | 다중 인스턴스 시 정합 어려움 |
| Redis | 다중 인스턴스 공유, 만료/패턴 무효화 강력 | 인프라 추가 |
| nginx proxy_cache | 정적 응답 빠름 | 사용자별 응답 캐싱 어려움 |

### 결정

**1차 Caffeine, 2차 K8s 다중 인스턴스 전환 시 Redis 이전.**
- 1차 단일 노드 운영 가정(SPEC-CMS-001 ASSUM-01)
- Spring `@Cacheable` 추상화 그대로 사용 → 캐시 매니저 교체만으로 전환

## 8. 멀티사이트 지원 깊이

### 검토 옵션

| 옵션 | 장점 | 단점 |
|------|------|------|
| 모든 도메인 테이블 site_id 보유 + 1차는 단일 row | 후속 활성화 시 코드 변경 최소 | 1차에 약간의 over-engineering |
| 단일 사이트 가정, site_id 컬럼 없음 | 1차 단순 | 2차 도입 시 모든 테이블 마이그레이션 |
| 처음부터 멀티사이트 활성화 | 일관 | 1차 범위 초과(SPEC-CMS-001 §3.2 비목표) |

### 결정

**컬럼은 모두 보유, 활성화는 후속 SPEC.** 모든 도메인 테이블에 site_id NOT NULL FK를 두고 1차에는 단일 site row만 시드한다. POST /content/sites는 SPEC-CMS-004-D-3에 따라 1차에 거부. 본 결정으로 멀티사이트 도입 시 데이터 마이그레이션 없이 활성화 토글만으로 전환 가능.
